# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

A computer-vision tool that watches street-camera footage and counts four independent categories of traffic — cyclists, pedestrians, cars (cars/buses/trucks), motorcycles — as they cross a vertical counting line. Built specifically for camera CAM 4 in Andradas (Intelbras, 1920x1080 @ 15fps, side-on view), but works with any fixed-camera footage. The code is in English; the app UI is multi-language (see "Languages" below). Up to 0.0.7 everything was in Portuguese — `web/src/lib/legacy.ts` migrates old data, and old folders/keys are still accepted where noted.

Two entry points share the same core (`counter/`):
- `process_video.py` — batch mode: reads a video file end-to-end, writes an annotated H.264 video + a JSON report.
- `stream_realtime.py` — real-time mode: reads RTSP/webcam/file, emits newline-delimited JSON events to stdout (for piping into Kafka/MQTT/a database), optionally shows a live OpenCV window.

## Architecture

**Single YOLO inference per frame (class-agnostic NMS), then 4 trackers + arbitration.** `TrafficCounter.process()` (`counter/detector.py`) is the shared core used by both entry points:

1. One `YOLOv8n` (COCO) call detects person/car/bus/truck/motorcycle with `agnostic_nms=True` (prevents car+truck double boxes). A SECOND model — `BICYCLE_MODEL` in config.py, a yolov8n fine-tuned on this camera with synthetic motion blur (`runs/ft_blur/weights/best.pt`, built by `evaluation/build_dataset.py` + `evaluation/train_finetune.py`) — supplies ONLY the `bicycle` detections. The fine-tune recovers blurred dusk/night bicycles (h17: 35→56 of 70 manual; h18: 10→32 of 85) without touching the other classes. Set `BICYCLE_MODEL = None` to fall back to COCO-only. Do NOT train with unlabeled night frames (blurred unlabeled vehicles teach the model that night objects are background — this was tried and it collapsed night car counts).
2. **Cyclists are counted from the `bicycle` class** (own tracker + line — project decision: vehicles carrying bikes essentially never pass here), with two recovery paths: a person track with bike association whose crossing pairs with no bicycle event within ±45 frames counts as cyclist ("cyc_person"); a bike track that dies without crossing the line but moved ≥350 px counts once ("screen" — Cristiano counts bikes that pass through the SCREEN, not only line-crossers).
3. **Persons** are tracked in a single tracker; each person track accumulates, frame by frame, whether a bicycle or motorcycle was nearby (anisotropic: |dx|≤120, |dy|≤250 px). When a person crosses the line it counts as **pedestrian** only if its track is NOT bike-associated (that's the cyclist, already counted via bicycle) NOR moto-associated (rider/pillion, already counted via motorcycle). Track-level (not per-frame) classification prevents double counting when bicycle detection flickers.
4. **Motorcycles** go through bike↔moto arbitration at count time: a motorcycle crossing event that coincides with a recent, consistent bicycle track (COCO confuses the two classes on two-wheelers) is discarded as a misclassified bicycle.
5. Cars (car+bus+truck) count directly. Each category has its own `sv.ByteTrack()` and `CountingLine`.

**`CountingLine` (`counter/line.py`) is the trickiest piece of logic in the codebase** — read it fully before touching counting behavior. Philosophy (v2, Jul/2026): **only actual line crossings count**. It does NOT use `supervision`'s `LineZone` (fails on large/fast objects). Counting paths (event `reason`), mutually exclusive per ID:
- `centroid` — track persists and its `cx` switches sides of `line_x`.
- `centroid_gap` — the SAME tracker id disappears for a few frames and resumes on the other side (ByteTrack re-association) — the crossing happened during the gap.
- `reid_opposite` — a NEW id appears on the opposite side of a recently-lost id, with physical plausibility checks: vertical coherence (`vertical_dist`), implied speed ≤ `reid_max_speed` px/frame × gap, and motion-direction consistency with the lost track's velocity (EMA `dx`). Without these checks this path both double-counts and suppresses real counts (platoons of cars in the same lane).
- `entry` (legacy, OFF by default, `count_on_entry`) — counts on frame-edge entry; direction inferred from which edge (right edge → moving left = in). The old always-on version counted objects that never crossed and inverted directions.
Same-side re-ID (`same_side_window`, `spatial_dist`, `vertical_dist`) merges broken tracks without counting; a new id adjacent to an already-counted ACTIVE track inherits "counted" (duplicate YOLO boxes). `_counted` guarantees idempotency; expired lost-ids are pruned.

When changing counting logic, preserve idempotency AND the plausibility checks in `_opposite_side_pair` — both directions of error (double-count and suppressed-count) came from that path historically.

**Known limitation (night)**: heavy motion blur under artificial lighting makes the `bicycle`/`motorcycle` classes undetectable while the rider is still detected as `person` → night cyclists/motorcyclists get counted as pedestrians. A speed-based reclassification fallback exists but is disabled (`CYCLIST_SPEED_THRESHOLD_PX_FRAME = None`) because ByteTrack id-switches poison track velocity.

**DVR seek quirk**: `cap.set(CAP_PROP_POS_FRAMES)` lands ~30 s early on these files and `get()` silently reports the requested position. Any frame extraction for visualization/verification must decode sequentially (`evaluation/exact_frames.py`). The processing entry points always read sequentially, so their frame numbers are the ground truth.

**Category-specific config lives in `config.py`**, not hardcoded — `LINE_X` (counting line position), `CONFIDENCE` (detection confidence threshold), `MAX_CYCLIST_DIST_PX` (person↔bicycle association distance), and the COCO class-ID groupings per category. This is the first place to look when adapting the tool to a different camera/location.

**Video writer abstraction (`process_video.py::_Writer`)**: pipes raw frames to `ffmpeg` (system install or the one bundled via `imageio_ffmpeg`) to encode H.264, falling back to OpenCV's `mp4v` writer only if no ffmpeg is found anywhere. This keeps output file size close to the original instead of the much larger default OpenCV codec.

**`counter/visualizer.py`** (`annotate_frame`) draws bboxes/traces/labels per category in a distinct color, the counting line, a red screen-flash on any new count event, and the stats panel — purely cosmetic, only invoked when annotated video output is requested (skipped entirely by `--no-video`).

App worker: `worker/detect.py` (complete trajectories → candidates, filmstrip/context/clip) reads video through `worker/reader.py` (ffmpeg NVDEC + `scale_cuda`, YUV output; needs the BtbN build in `~/.local/opt/ffmpeg-btbn` or `TRAFFIC_COUNTER_FFMPEG`, otherwise falls back to the CPU). Videos > 1920 px are processed at 1080p; `imgsz` follows the source resolution (4K → 1280).

Analysis area (Oct/2026, `--area x,y,w,h` in 0–1; `jobs.area`/`cameras.area`): the reader crops the frame BEFORE scaling (`crop` before `scale_cuda`, checked on the 1st frame against the CPU — an old FFmpeg could ignore it on CUDA frames) and the worker detects only in the crop, at full resolution. Why: Augusto de Lima (4K, high camera) — the ~60 px cyclist became ~17 px at 1080p and neither YOLO nor motion caught it (0 of 6). In the crop, YOLO still fails (blurred cyclist, person 0.28 < `CONFIDENCE` 0.4); motion catches it, with the finer mask (up to 960 px) and **counting the shadow** from MOG2 (`fine`: threshold 100, 11×11 closing) — the blurred cyclist over the pavement came almost entirely marked as shadow. Coordinates: the "processed frame" becomes the crop; `scale_of` = pixel density relative to 1080p (native 4K crop → 2); `lines_in_frame` converts the lines, `box_in_original`/`save_points` return boxes and points to the whole frame. `tracks_meta.json` stores the area (`area_arg`): changing the area redoes the detection (the runner compares in `tracksArea`). In the line editor, the area is on by default for videos > 1920 px and follows the lines (margin, minimum ~1/4 of the frame) until the user draws one; it warns about a line outside the area and an area > 1920 px (downscaled). The final video does not change. In the area, the fine mask lets noise through (10–20 px specks at 4K: compression, sun through the leaves) that the tracker chains into "tracks" that jump around: `_real_motion` with `fine` requires the area p90 ≥ `MOTION_FINE_AREA_P90` and displacement ≥ `MOTION_FINE_SHIFT` (1080p px; 30 discarded → 3 without losing a cyclist). A car **tight** in the area: the box of the car in the lane next to the curb comes down over the bike lane — enlarged, it "explained" the cyclist beside it and spliced the blobs; there it is not enlarged and its core leaves the mask (recovers the cyclists glued to the car at 81 and 117 min). `tracks_meta.json` stores `motion_fine` (`MOTION_FINE_VERSION`): older area tracks are redone. Bicycles in the area: the fine-tuned model (`BICYCLE_MODEL`, Andradas camera) catches nothing at Augusto de Lima and COCO does — in the area, COCO's bicycles add to its own (NMS); and COCO alternates bicycle/motorcycle on the same small cyclist, which kept both trackers from forming a track — in the area, two-wheelers go to a single group (`bike`) and the vision model decides. Without this, the raw "person" box (too fast for ByteTrack's IoU) still "explained" the blob and the cyclist vanished (88 min). Removing cars from detection did not help (cars become blobs and all go to the vision model). Test variations on 30 s clips cut with `ffmpeg -ss … -c copy` (minutes, instead of ~45 min for the whole video); cropping detection with a margin around the area did not help and was ~3× slower.

Detection preview: the worker overwrites `preview.jpg` (current frame with boxes and lines, ≤ 1280 px) once per second and deletes it at the end; the job page shows it instead of the 1st frame.

A YOLO car (`origin` track, `yolo_class` cars) on a line that does not count cars does not go to the vision model (`startSuggestions`): it records the suggestion with `llm_model = NO_CONSULTATION` ("detector") and goes into the bulk accept (Augusto de Lima: the model confirmed 236 of 236). A motion blob still goes to the model — it may be the cyclist glued to the car.

Review (phase 3): `web/src/app/jobs/[id]/review.tsx` + `web/src/lib/review.ts`. The proposal for each candidate is the model's suggestion, replaced by a discard when the category is not counted on the crossed line (`Line.categories`, editable in the line editor and in the review itself without redoing anything). The human decision is in `candidates.label`; the totals and the final video use only `label`. Shortcuts: ↑/↓, Enter accepts, 1–8 categories (1 cyclists, 2 pedestrians, 3 cars, 4 motorcycles, 5 kick scooters, 6 mopeds, 7 unicycles, 8 other), 0 discards, U undoes; ←/→ one frame (Shift: 1 s), Space/P plays, +/− zoom, `\` whole timeline. Space no longer accepts the proposal (easy to press when wanting to play the video), and Enter/Space with a focused button go to the button.

Timeline (`timeline.tsx`) in editor style: ruler with a draggable cursor, zoom down to the frame (Ctrl+wheel anchored at the mouse, −/+, slider, "Fit"), dragging the background moves the view, adjustable height (`localStorage` `tc:timelineHeight`), option of one track per line × category; draws only marks and labels of the visible range. The cursor (`clock.ts`) lives outside React state — it changes every frame while playing. The monitor has the **Video** tab: the original (`/api/jobs/[id]/video`, with Range; HEVC opens in Chromium/Electron with hardware decoding) at the cursor frame, with lines and area on top and frame/speed controls. **DVRs have time gaps** (Andradas_06: 54,009 frames in 3,631 s): the worker counts frames, the `<video>` uses the recorded time — `lib/mp4.ts` reads the stts/ctts/elst table from `moov` (no decoding, ~10 ms) and `/api/jobs/[id]/frames` serves it; the review positions each candidate by `table[frame]` (without it, the cyclist at frame 1315 showed 0.7 s early, and the difference reaches ~30 s at the end of the hour). **Possible duplicate** filter (`possibleDuplicates` in `review.ts`): same line, direction and class, crossing within ≤ 1 s with overlapping boxes — only points it out, does not discard.

Everything that moves goes into the review: besides YOLO's 4 ByteTracks, `worker/detect.py` runs background subtraction (MOG2 on a 480 px copy) and tracks the blobs no YOLO box explains (group `motion`, origin `motion`, `yolo_class` = `other`); they only become candidates if they last ≥ 0.6 s and move ≥ 1.5 heights, and are dropped if they coincide with a YOLO event on the same line. On a line that does not count cars (bike lane, sidewalk), an object whose length in the crossing direction is > `LANE_WIDTH` (3×) the line's does not become a candidate: the base of the box of a car/bus in the next lane (and the headlight on the ground) invades the bike lane. Categories only from the vision model: kick scooter, electric moped, unicycle; what moves and has no category goes to **other** ("none"/discard is only for what is not a real object).

Final video (phase 4): `worker/render.py` + `web/src/app/renders/`. A render joins one or more jobs with a complete review, in the chosen order (home page, or the review's button for a single one), into a single 1080p MP4; the panel adds across the videos (lines with the same **name** are the same count). The user chooses which categories go in (`renders.categories`, JSON; null = all — `CategoryPicker` in the review, in the home page tray and in "Generate again"); the runner filters the events and the lines' categories when building the plan, and `render.py` removes from the panel what was left out. The plan (`data/renders/<id>/plan.json`) freezes the `label`s at request time — the page warns when the review changed afterwards and offers to generate again. Output: `final_video.mp4` (h264_nvenc, or libx264 without NVIDIA; capped at 2 Mbit/s), `report.json`, `events.csv` (`;`, BOM for Excel; header in the app language). Reading and writing in threads (~135 fps; 2 h ≈ 13 min). Accented text via PIL (OpenCV's Hershey has none).

The context sent to the model needs the object's box: the crossing usually falls between two track observations, and `_box_at` interpolates the box (without it the model classified the neighbor — e.g. the cyclist next to the car). The prompt says to classify only the marked object.

Visible errors (Oct/2026): each suggestion failure stores in `candidates.llm_error` the JSON with HTTP status, attempts and what OpenRouter/the provider answered (`OpenRouterError.detail`), and goes to `suggestion_errors.jsonl` in the job folder and to the server log (`[suggestions] …`). Vision model (OpenRouter): default `anthropic/claude-haiku-5.5`, filmstrip + context, no YOLO hint. The prompt is per language (`web/src/lib/prompts.ts`: instructions, the category word the model answers with — mapped back by `parseCategory` — and the language of the `reason` shown in the review); the job uses the app language at detection time. Calibration (Oct/2026): `evaluation/build_llm_calibration.py` matches Cristiano's labels (`rotulos_andradas.json`, on the Drive — its format stays Portuguese, the labeling page is his) with worker candidates; `web/scripts/calibrate.ts` compares models (`--locale` for another prompt language), and `web/evals/` (promptfoo) compares the languages. Audited ground truth in `evaluation/llm_calibration_audited.json` (142 cases, almost all dusk/night): Haiku 5.5 99–100%, Gemini 3.1 Flash Lite 99% at 4× the cost, YOLO alone 87% (13/32 cyclists).

Images for the model: Claude refuses a side > 8000 px ("Provider returned error" from Vertex). Very wide motion blobs (the whole sidewalk curb at dawn, ~1900×40 px) produced 8–14 thousand px filmstrips — those were Cristiano's persistent failures (6 of 491 on Andradas_06, all `motion`). `save_filmstrip` fits each crop in 480×160; for old jobs, `suggestCategory` reads the JPEG size (`jpegSize`) and sends only the context if the filmstrip exceeds `MAX_IMAGE_SIDE` — "Try again" fixes it without redoing the detection.

Model fallback (Oct/2026): `suggestCategory` sends `models: [main, ...fallbacks]` and OpenRouter moves to the next when one fails at run time (provider down, 429, "Provider returned error", model without image support); an invalid model ID is refused before routing and does not fall back. `DEFAULT_FALLBACKS` = DeepSeek V4.1 Flash 1017 → Gemini 3.1 Flash Lite; `OPENROUTER_FALLBACK_MODELS` replaces it (empty/"none" turns it off; the old `OPENROUTER_MODELOS_RESERVA` still works); `calibrate.ts` passes `fallbacks: []` to measure one model at a time. ## Output data model

Both entry points produce events keyed by category (`cyclists`/`pedestrians`/`cars`/`motorcycles`), each carrying a running total plus `in`/`out` directional counts (`in` = right→left, `out` = left→right, per `CountingLine`). `process_video.py` accumulates these into one `result.json` at the end; `stream_realtime.py` emits them as they happen (plus `start`/`heartbeat`/`shutdown` lifecycle events) so downstream consumers don't need to wait for the stream to end.
